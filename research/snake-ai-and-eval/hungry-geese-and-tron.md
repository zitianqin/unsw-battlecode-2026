# Hungry Geese (Kaggle 2021) and Tron AI: lessons for UNSW Battlecode 2026

Legend: VERIFIED = read in a primary source this session (URL given). INFERENCE = my reasoning. UNVERIFIED = claimed somewhere / from memory, not confirmed.

## 1. Kaggle Hungry Geese (Jan-Jul 2021)

### 1.1 Rules (VERIFIED from env source)
Source: https://github.com/Kaggle/kaggle-environments/blob/master/kaggle_environments/envs/hungry_geese/hungry_geese.py and `hungry_geese.json` in the same dir.
- Board 7 rows x 11 cols (defaults `rows=7`, `columns=11`), **torus**: `translate()` does `row % rows`, `col % columns`.
- 4 geese in competition (env supports 1-8 agents). Start as length-1 at random distinct cells. `episodeSteps=200`. `actTimeout=1` s per step plus `remainingOverageTime=60` s bank.
- **Simultaneous moves.** Actions NORTH/EAST/SOUTH/WEST. Reversing into your previous direction = instant death (even at length 1).
- Order inside one step (per goose): move head; if head on food, eat (no tail pop) else pop tail; self-collision check against own (post-pop) body; every `hunger_rate=40` steps pop one more tail segment, length 0 = starved. Then global check: **any head on a cell with >1 segment dies**. So head-on = both die; head into a body = only the mover dies; moving into the cell another goose's tail just vacated is safe (tail popped first) unless that goose ate this turn.
- `min_food=2` food always on board, respawned uniformly at random on free cells (NOT predictable; ours were predictable from a fixed seed until 2026-09-25, now seeded randomly per match).
- Reward = `(steps_survived+1)*(max_length+1) + length`: survival time dominates, length breaks ties. Ranking in a game is by this reward; last goose alive is set DONE (game ends).
- Ladder: TrueSkill/Elo-like rating (~600 start), many 4-player games per day; final ranking after a ~2-week settle period. (Rating details UNVERIFIED beyond write-ups quoting "~1100", "~1200" LB scores.)

### 1.2 Top solutions

#### 1st place: team "HandyRL" (DeNA: Katsuki Ohto @YuriCat, Kazuki Tanaka @kyazuki): self-play RL net + rollout DUCT ensemble
- VERIFIED that HandyRL won: HandyRL README links "The 1st place solution in Hungry Geese" -> https://www.kaggle.com/c/hungry-geese/discussion/263279 (https://github.com/DeNA/HandyRL). That Kaggle topic is now **deleted** (internal API returns `isDeleted: true`, 26 messages); Wayback snapshots are JS shells without body text. So details below come from DeNA's own blog, not the write-up.
- Method, per DeNA engineering blog (https://engineering.dena.com/blog/2021/12/distributed-reinforcement-learning-with-handyrl/, Japanese; read via fetch+translation, so treat numbers as VERIFIED-but-translated):
  - Moves chosen by an **ensemble of a deep-RL agent and a look-ahead (MCTS) agent**. The search used **simulation (rollout) evaluation, thousands to tens of thousands of simulations per second**, with Go-engine-style fast board code, and **Decoupled UCT** ("multiple players' bandits at one node") for simultaneous moves. Stated motivation: self-play RL alone is weak at tactical reading and at situations requiring anticipation of adversarial/cooperative behaviour.
  - RL: ~3 weeks of self-play, ~16M games, then ~4 days vs diverse opponents, ~3M more games. Input 4x8x7x11 per-player + 5x7x11 global features; 3x3 conv net with torus padding.
  - Held 1st for ~3 months; nearly lost in the final settle period (briefly 2nd with a day left).
  - Exact ensemble rule (how RL policy and MCTS stats were combined) UNVERIFIED.
- HandyRL (open source, released 1 Mar 2021, https://dena.ai/news/202103-handyrl/): distributed off-policy policy gradient; targets MC / TD(lambda) / V-trace / UPGO. Public geese baseline `GeeseNet` = 12 torus-padded 3x3 conv layers x 32 filters, 17 input planes, policy head + value head (https://github.com/DeNA/HandyRL/blob/master/handyrl/envs/kaggle/hungry_geese.py). Its public notebook (topic 218190, "Rating ~1100, February 10") became the base for a large share of the top 20 (3rd, 6th, 9th, 11th all cite HandyRL).
- HandyRL team won February 2021 monthly prize (https://dena.ai/news/202103-handyrl/).

#### 2nd place: "Goosebumps" (Isaiah Pressman @pressman1, Liam Kirwin @lpkirwin, @vishyvishal): behavioural cloning + PUCT MCTS (VERIFIED)
Source: https://www.kaggle.com/competitions/hungry-geese/writeups/goosebumps-goosebumps-solution-2nd-place (read via Kaggle internal API `discussions.WriteUpsService/GetWriteUpBySlug`); code https://github.com/IsaiahPressman/Kaggle_Hungry_Geese
- **Net trained by imitation, not RL.** Supervised on daily-downloaded top-agent replays: policy for all 4 geese (cross-entropy, +0.1 entropy bonus so priors stay soft) and final outcome (MSE). Augment: H/V reflections, permute agent order. Architectures are translation-equivariant on the torus (circular padding), so no translation augmentation.
- **Data filtering was the lever:** keep only episodes where the *worst* agent's current LB score > threshold t; raising t "almost always" gave a notable strength jump while data sufficed.
- Input 19x7x11: per goose {head, tail, head-last-turn, body with value n/100 counting from tail}; + food, steps since last starvation, current step. Best model: CNN, 6 SE-residual blocks x 64 ch, circular padding, no norm. 8x128 attention (torus relative position) also strong. Policy heads read the hidden vector at each goose's head cell; values softmax-normalised so they sum to 0 across geese.
- **Search mattered a lot:** "the base model's predictions are not very strong on their own" (it imitates the average agent's mistakes). PUCT MCTS over joint actions (each goose picks by PUCT; this is decoupled selection), only ~20-50 iterations/s in pure Python. Tricks: mask instant-death moves; ignore food when hashing states (accepting bias to search deeper); if the search policy is moving fast toward a less-likely action (shift >0.12) pick it early; spend overage time only when the search is uncertain (extra 0.5 s chunks, cap 3 s, stop below 2 s bank).
- **Head-on fix = opponent-noise model:** their best agents too often "place 3rd due to head-on collisions with a shorter goose that the neural network predicted would never move towards us." Fix: opponent policy = (1-w_i)*net + w_i*uniform, with w_i fitted online per opponent by gradient descent on KL vs. that opponent's actual moves this game. Unpredictable opponents get flattened priors, so search respects their possible head-on moves.
- Tried and weaker: self-play A2C/IMPALA on GPU (5-6 games/s, competent in an hour) but policies too deterministic to help MCTS; combining NN policy with fast compiled search; AlphaZero-in-the-loop (too slow).
- **Hand-crafted MCTS (Kirwin), no ML:** topped the LB early; final score ~1189, "a little outside the top 10". Numba 30-40k states/s, then Rust ~300-400k states/s (10x) but "only modest gains": deeper search finds forced wins/dead ends 10-20 steps out, but the real weakness was **mispredicting opponents**. Details: nodes keyed by actions only, re-simulate from root with random food each iteration; risk aversion = blend of mean value and worst-case over opponent replies; two exploration terms (per-agent move and joint-move combination: "fairly big boost"); priors = instant-death moves very unlikely, food slightly likely; value = rank scores [-1,-1/3,1/3,1] for dead geese, remaining points split by length for living ones. Flood-fill value was slower and "made the agents a bit worse". Testing: scenario regression tests mined from replays ("episode X, step 154, red must go south").

#### 3rd place: Maxwell (@hoxomaxwell), LB 1239.1: imitation + HandyRL RL + modified MCTS (VERIFIED via slides)

#### 5th place: takedarts "GeeseZero" (AlphaZero-style, no external data) (VERIFIED)
Source: https://www.kaggle.com/competitions/hungry-geese/discussion/263702 ; code https://github.com/takedarts/hungry-geese
- Pure self-play AlphaZero loop, no replays, no RL framework. ~350k self-play games on one Threadripper 3970X; train on latest 60k games; gate new model by evaluation games.
- Self-play trick: one search tree picks all 4 geese' moves (4x faster than 4 agents) but then geese "know" each other's moves and dodge collisions too well, so a **penalty for moving to potential-collision cells** was added.
- Food randomly removed from training inputs, because inside search the net sees boards where food got eaten.
- Input 98x11x11: board shifted so own head is centred and **rotated so the goose faces north** (policy = left/straight/right). ResNet: stem to 64x7x7, 8 pre-activation residual blocks with positional embedding. Outputs: 3 policy (L/S/R), 3 values = P(1st), P(2nd), P(3rd); sigmoid + MSE.
- Search: **DUCT** (Decoupled UCT: each player runs its own bandit at a node, joint action = tuple of individual picks). UCB1 "does not seem good"; replaced by custom score (v_parent*p_i + sum v_ik)/(1+n_i)^1.5. Values normalised to sum to 1 across players, which makes the agent "not only survive but also hunt other geese".
- Plus a non-predictive dead-end look-ahead used only as a move filter. Tunable knobs: collision penalty, eat bonus, safe (survive vs win), value bonus for alive, bonus for head near own tail.
- Only **40-60 search iterations per move** on Kaggle (Numba, torch 1 thread), still 5th.

### 1.3 Lessons from Hungry Geese
1. **Search on top of the net mattered at the top, but not universally.** 1st (RL+rollout DUCT ensemble), 2nd (BC+PUCT: "base model's predictions are not very strong on their own"), 3rd, 5th, 11th all searched. 6th used no search. Iteration counts were tiny (5th: 40-60/move; 2nd: 20-50/s) when the NN was inside the tree; the rule-based-rollout searches ran 1e3-4e5 states/s. (VERIFIED from the write-ups above.)
2. **Simultaneous moves -> decoupled search.** 1st, 5th, 11th used DUCT; 2nd used per-player PUCT selection (also decoupled). Kirwin found an extra exploration term over *joint* move combinations gave a "fairly big boost". (VERIFIED.)
3. **Head-on collisions are an opponent-modelling problem, not a search-depth problem.** 2nd place's main failure was head-ons with opponents the net thought would never come at them; fix was per-opponent online-fitted uniform-noise mixing. Kirwin: 10x more speed (Rust) gave "only modest gains" because the error was opponent misprediction. 11th used risk-neutral rewards but exploited deterministic clones. 5th had to *add* a collision penalty because single-tree self-play made geese dodge too perfectly. (VERIFIED.) INFERENCE: worst-case/paranoid blending on head-adjacent cells is the cheap version of this.
4. **Imitation from leaderboard replays is a fast bootstrap and, with search, reaches 2nd.** Key: filter by the *weakest* player's rating in the game and keep raising the bar; mix entropy regularisation so priors stay soft for search. 3rd/11th/IMOKURI did imitation -> RL -> (re-)imitation. (VERIFIED.)
5. **Symmetry/ego-centric encoding.** Torus-equivariant convs (circular padding) or head-centred, heading-rotated inputs (5th, ironbar) remove translation/rotation augmentation. (VERIFIED.)
6. **Flood fill as a feature, not as the value function.** 3rd and 9th used flood-fill/influence features or guards; Kirwin's flood-fill *value* made search slower and weaker. (VERIFIED.)
7. **Evaluation is the bottleneck.** Huge variance (ktechb), slow MCTS self-matches (Kirwin); workarounds: replay-mined regression scenarios, fixed gauntlets with +5/+1/-1/-5 scoring (6th), 224-game gates at 55% (3rd). (VERIFIED.)

## 2. Tron / light cycles

### 2.1 Google AI Challenge 2010 (Tron), Univ. of Waterloo CSC + Google, Feb 2010
Game: 2 players, simultaneous moves on a walled maze; each move leaves a permanent wall; crash into any wall/trail loses; both crash or both enter the same square = draw (per Den Teuling & Winands, 2.2). ~1 s per move (a1k0n's code uses `TIMEOUT_USEC 990000`). ~700 entrants (quotenil). Final ranking by Elo.
Final top (VERIFIED, archived rankings https://web.archive.org/web/20110807101435/csclub.uwaterloo.ca/contest/rankings.php): 1 a1k0n_ (Andy Sloane, C++, 2820), 2 aramadia 2731, 3 kduleba 2730, 4 hebbie 2726, 5 Janzert 2723, ... 11= bocsimacko (Gabor Melis = quotenil, Common Lisp, 2673). Top ~20 almost all C++.

#### Winner a1k0n: evaluation beats depth (VERIFIED, https://www.a1k0n.net/2010/03/04/google-ai-postmortem.html ; code https://github.com/a1k0n/tronbot tag a1k0nbot-2.18.2)
Chronological build, each step a measurable gain:
1. **Space-filling (fill mode):** "always choose the move that removes the least number of edges from the graph", i.e. hug walls; avoid **articulation points (cut vertices)**, and if you must enter one pick the largest remaining side. Initially approximated cut vertices with a 3x3-neighbourhood lookup table (`artictbl.h`); connected components via 2-pass raster union.
2. **Minimax + alpha-beta, iterative deepening**, with the **Voronoi heuristic**: each cell belongs to whoever reaches it first (BFS/Dijkstra from both heads); score = my cells - their cells. Lesson learned: on timeout, discard the half-searched ply and use the previous iteration's best move.
3. **Separated-space endgame:** once players are in different components, value = 1000*(my component size - theirs) inside search; when actually separated, just run the greedy wall-hugger (no search), later upgraded to an iterative-deepened exhaustive search with the greedy filler run to completion at the leaves.
4. **Territory bonus for edges:** count open-neighbour edges in your Voronoi region, which produces wall hugging when otherwise equal.
5. **Data-mined eval weights:** scraped the contest server's replays (11,691 games of top-100 players), found the separation point, regressed endgame move difference on Voronoi stats: predicted diff = K1*(N1-N2) + K2*(E1-E2), K1=0.055 (nodes), K2=0.194 (edges). "Definitely improved play." Kept 14 bot versions for local comparison; "no bot ever totally shut out a previous bot on all maps."
6. **Checkerboard parity** (from forum user dmj): moves alternate colours, so surplus squares of one colour are unreachable; gives a tighter upper bound on fillable space and lets endgame search stop early when the bound is met.
7. **Chamber trees / battlefront (the contest-winning idea, by his account):** find articulation points (standard O(N) algorithm), treat the space as a tree of chambers. DFS from own chamber; for each neighbouring cut vertex, child value = current chamber + child if child is not a "battlefront" (touches opponent's Voronoi region), else only the steps to enter the child. Return max over children. This models that you can't both fight at the front and fill the chambers behind you. Won 12-1 vs the previous version.
- Quote: "a better evaluation heuristic will always beat deeper minimax searches, because a deep minimax search using a flawed evaluation heuristic is self-deluded about what its opponent is actually going to do."
- **Simultaneous moves handled by serialising** (VERIFIED from `MyTronBot.cc` `_alphabeta`): player 0 picks, player 1 then picks *knowing* player 0's move, and both positions are applied only after player 1's ply; head-to-head same cell returns `DRAW_PENALTY` (0). That is a paranoid (opponent-moves-second) approximation of a simultaneous game.
- Weakness he admits: large random maps (endgame exhaustive search "works terribly") and endgame miscounting of opponent space.

#### quotenil (Gabor Melis, 11th/700, best non-C++) (VERIFIED, https://quotenil.com/google-ai-challenge-2010-results.html)
- Went in planning **UCT (MCTS)**; abandoned it: a random default policy "kept cornering itself in a big area faster than another player could hit the wall at the end of a long dead end"; concluded "Tron is simply too tactical ... for MC to work really well". Best UCT-based entry finished **105th** (jmcarthur).
- A 1-ply territory (Voronoi) eval with no opponent modelling already "played a very nice positional game".
- Final: alpha-beta + principal variation + iterative deepening; parity trick; graph-partitioning (chamber) eval used only in separated endgame.

### 2.2 Maastricht MCTS-for-Tron papers (VERIFIED, PDFs read)

**Den Teuling & Winands, "Monte-Carlo Tree Search for the Simultaneous Move Game Tron"** (https://dke.maastrichtuniversity.nl/m.winands/documents/Tronpaper.pdf ; year ~2011-12, UNVERIFIED)
- Tree modelled as turn-taking (root player moves first); fix for simultaneity: when the root player moves onto a cell the opponent could also have entered, add a **terminal draw child** so the search can't pretend it "claimed" a contested cell first.
- Score-Bounded MCTS-Solver (handles draws) helps (53% vs UCT) and plays shortest proven wins.
- **Predictive expansion:** once players are separated, estimate space (greedy wall-follow fill = lower bound; checkerboard parity M = Z - |c_grey - c_white| = upper bound) and make the node terminal. **Play-out cut-off** every 5 moves with the same estimate. Gains are board-dependent (+3..8% on 2 boards, worse on the third).
- Play-out policy round robin: plain random (minus instant-death moves) was the most robust; "offensive" (move toward opponent) was terrible (4-13% vs others); defensive strong on one board.
- **vs a1k0n (alpha-beta + chamber-tree eval): best MCTS variant won only 18 +/- 3%**; a1k0n won >85% vs the rest. Cause: play-out reliability "rapidly drops as the players get more distant", so MCTS realises it's lost too late. Confirms quotenil's finding that Tron is too tactical for plain MCTS.

**Lanctot, Wittlinger, Winands, Den Teuling, "MCTS for Simultaneous Move Games: A Case Study in the Game of Tron" (BNAIC 2013)** (https://dke.maastrichtuniversity.nl/m.winands/documents/sm-tron-bnaic2013.pdf)
- Two tree models: sequential (searcher moves first; "clearly favours one player which is especially problematic when players are close to each other") vs **stacked matrix** (child per joint move).
- 8 selection variants, 500-game matchups on 4 boards. Overall: **Decoupled UCB1-Tuned (max) 62.3%**, DUCB1T(mix) 54.8, sequential UCB1-Tuned 54.3, Regret Matching 53.1, sequential UCT 51.4, DUCT(max) 49.1, DUCT(mix) 39.5, Exp3 35.5.
- Authors' reading: "a better way of performing exploration has a bigger impact on performance than the choice of the game model (sequential versus stacked matrix)". Sequential UCT did OK because it plays safe (assumes the opponent sees its move). On a 6x6 board everything ~50%.
- "(max)" = play the most-rewarding action at the end; "(mix)" = sample from visit-count distribution. In Tron, deterministic (max) beat mixing.

**Lanctot, Lisy, Winands, "MCTS in Simultaneous Move Games with Applications to Goofspiel" (CGW 2013)** (https://dke.maastrichtuniversity.nl/m.winands/documents/wcg13-smmcts.pdf)
- Theory side: DUCT does not converge to a Nash equilibrium (Shafiei et al. counter-example); sequential-tree UCT for Tron gives one player "unrealistic informational advantage". Introduces Online Outcome Sampling (OOS, provably converges to NE); Regret Matching and OOS+ best head-to-head in Goofspiel (e.g. RM 63.3% vs DUCT(max), 53.2% vs DUCT(mix)); all variants less exploitable than UCT.
- INFERENCE: equilibrium mixing matters in games like Goofspiel where bluffing/mixing is the point; in Tron-like games (and Hungry Geese) the empirical winners were deterministic decoupled bandits (DUCB1T(max), DUCT) plus good evaluation. Related work cited: Perick et al., "Comparison of different selection strategies in MCTS for the game of Tron", IEEE CIG 2012, pp. 242-249 (not read).

### 2.3 CodinGame Tron Battle (2014 contest, still a ladder game)
- Contest ended 28 Feb 2014; 1,564 tried, 672 submitted; top 3 ThomasNzO, yvesmocq, hau (VERIFIED https://www.codingame.com/blog/end-of-tron-ai-battle-congrats-everyone/). No winner write-ups found; CG did not publish sources. Winners' methods UNVERIFIED.
- Rules relevant to us (from https://github.com/nathanWolo/tron-codingame README, a hobbyist Rust bot; not cross-checked against the official statement, so UNVERIFIED): 30x20 grid, 2-4 players, **turns are sequential (player 0, then 1, ...), so no head-on same-cell collisions**; <100 ms/turn; a dead player's whole trail disappears.
- Community approach (forum, dolmen1234, https://forum.codingame.com/t/tron-battle-multiplayer-challenge-discussion/49/36): multi-player minimax "including all the players: depth n: you, depth n-1: other player 1, depth n-2: other player 2", eval Voronoi at the leaf; acknowledged as "pessimistic, because it considers that everyone is fighting against you, and it will reduce your horizon". Reported as enough for Legend (per search snippet; UNVERIFIED).
- nathanWolo's bot (same README): 1v1 iterative-deepening minimax + bitboard Voronoi; separated -> fill mode; 3-4 players -> **paranoid search where only the closest rival is a true MIN and other bikes play one greedy space-keeping reply** (cheap way to keep depth with many agents). Testing: SPRT vs frozen baseline, seat-rotated games on frozen random openings plus random seed plies (fishtest-style). Rank not stated.

## 3. Transferable to Battlecode 2026
Key differences first: our turns are **sequential by dragon id within a round** (like CodinGame Tron, unlike Hungry Geese / Google Tron), there are **up to 64 units per team, each a separate process with no shared memory**, the board is a **10-64 torus** (bigger than 7x11), bodies **move** (tails free cells, like Geese, unlike Tron's permanent walls), **splitting** exists, and pearl spawns were predictable from a fixed seed until 2026-09-25 (now seeded per match, like Geese food, though seen countdowns still tell when a tile spawns). Budget: 100M CPU points per dragon per turn in WASM.

1. **Put effort into the evaluation, not raw depth.** a1k0n won with alpha-beta whose gains came from eval upgrades (edges bonus, regression weights, chamber tree), and said deep search on a flawed eval is "self-deluded"; Kirwin's 10x Rust speedup gave "only modest gains". (2.1, 1.2)
2. **Core eval = multi-source BFS Voronoi on the torus**: which cells each of our heads reaches before any enemy head, scored as nodes + edges (a1k0n: K1=0.055 per node, K2=0.194 per edge, fitted by regression on 11,691 replays). Difference: our bodies shrink back from the tail, so a body cell should count as free once its "clears in t turns" is less than the BFS distance (Geese-style tail logic, 1.1). INFERENCE.
3. **Separated / trapped dragons need fill mode**: wall-hug (take the move that removes fewest free edges), avoid articulation points or enter the bigger side, checkerboard-parity upper bound, chamber tree. Directly useful for "is this dragon trapped / will it survive N turns" checks. With moving tails this is only an approximation; Kirwin found flood fill too slow as a search value but 3rd/9th Geese used it as a feature/guard. (2.1, 2.2, 1.2)
4. **Head-ons are an opponent-model problem.** Goosebumps' main loss mode was head-ons with geese the net thought "would never move towards us"; fix was per-opponent online noise w_i fitted to that opponent's observed moves. Deeper search didn't fix it (Kirwin). For us: treat every cell an enemy head that moves *later this round* can reach as dangerous, weighted by that enemy's observed aggression. INFERENCE for the exact rule. Engine check (main agent, `docs/unsw/death.md` + `execution-order.md`): head-on happens at move time, when a dragon moves its head into another dragon's head; so the later mover chooses whether to trade (see swarm-coordination.md §4).
5. **Use the sequential order.** Dragons with lower ids have already moved when we act, so their positions are exact; only later-moving dragons need modelling. CG Tron (also sequential) shows the cheap multi-agent pattern: paranoid search where only the **nearest** rival is a true minimiser and others get one greedy reply (nathanWolo), because full "everyone vs me" minimax is "pessimistic ... will reduce your horizon" (dolmen1234). (2.3)
6. **If searching simultaneous-ish local fights, use decoupled bandits, deterministic (max) move choice, and truncated rollouts.** Tron: Decoupled UCB1-Tuned(max) 62.3% overall; sequential tree "favours one player ... when players are close". Geese: 1st/5th/11th used DUCT; 11th capped rollouts at 10 turns with a heuristic rollout policy. Plain random-rollout MCTS lost to alpha-beta in Tron (best MCTS 18% vs a1k0n; best UCT entry 105th). (2.2, 2.1, 1.2)
7. **Head-on trade value is an eval term.** INFERENCE from our rules (not from the sources): a head-on kills both and drops ceil(L/2) pearls each, so a length-2 split dragon trading into a long enemy is a good trade and the reverse is bad. Top-ladder meta (2+2 splits, most deaths head-on) suggests small dragons as kamikaze screens. Geese normalised values across players (5th: sum to 1, which made geese "hunt"), the same idea of scoring relative outcome.
8. **No shared memory: plan jointly, act individually.** Geese 5th ran one tree choosing all four geese' moves (4x cheaper) but had to add a collision penalty because jointly-planned geese dodge too perfectly. INFERENCE: our dragons can each run the same deterministic team planner on the same observed state to get consistent assignments (pearl targets, who screens), but must not assume enemies coordinate like that.
9. **Imitation from ladder replays is a fast bootstrap.** Goosebumps reached 2nd with behaviour cloning + search, filtering games by the *weakest* participant's rating and raising the bar over time; a1k0n fitted his eval from scraped contest replays. Even without a net, replays give eval weights and **regression scenarios** ("episode X, step 154, must go south", Kirwin). (1.2, 2.1)
10. **Exploit determinism and build an evaluation harness early.** Until 2026-09-25 predictable pearls let us plan routes exactly; now only seen countdowns do (Geese had to average over random food). 11th place detected deterministic clone bots and predicted their moves exactly. Evaluation variance was the main bottleneck in Geese; use fixed gauntlets (6th: +5/+1/-1/-5 over 100 games), win-rate gates (3rd: 224 games at >=55%), and SPRT with seat rotation (CG Tron). (1.2, 2.3)
